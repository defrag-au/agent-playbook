# The benchmark site

`playbook.defrag.au` publishes the rig-eval results. It is a static site built from run
artefacts, served by an assets-only Cloudflare Worker. Nothing runs at request time.

The design copies two patterns from `cnft.dev-workers`, not its `sites/` pattern:

- **`projects/notebooks`** — one Observable Framework project, one worker, one deploy for every
  page. Adding a page is a markdown file, not a worker.
- **`projects/treasuries`** — `artifacts/` written by a tool; `src/data/*.js` loaders read them at
  build time and **fail the build** on a schema mismatch; the method page comes first.

`sites/` is Zola and Tailwind for marketing and legal pages. It has no data loaders, so it is the
wrong shape here.

## Decisions

| Decision | Choice |
| --- | --- |
| Domain | `playbook.defrag.au` (production), `playbook-dev.defrag.au` (dev) |
| Access | public, both environments |
| Tooling | `nodejs_22` and `wrangler` in the agent-playbook devshell |
| Run artefacts | committed under `site/artifacts/` |
| Worker | assets-only; no `main`, no bindings, no Rust |

## Layout

```
site/
  build.sh
  wrangler.toml
  artifacts/
    <run-id>/
      manifest.json        identity: corpus, checkout, snapshot, arms, model, totals
      summary.md           the generated tables
      traces.json          public projection: no answers, no session ids
      tools.json           one row per (scenario, arm, repeat, tool)
      checks.json          one row per check
      observable.md        the notebook source
      claim.md             authored; optional, never generated
  frontend/
    package.json
    observablehq.config.js
    scripts/sync-runs.mjs  artefacts → pages and loaders
    src/
      index.md             latest run and what this is
      method/index.md      corpus, scoring, cost, isolation, limits
      runs/index.md        every published run
      data/runs.json.js    scans artifacts/ for the index pages
      runs/<run-id>/
        index.md           claim + notebook (generated)
        tables.md          the generated tables (generated)
```

`artifacts/` is canonical. `src/runs/` and `src/data/` are generated by `sync-runs.mjs` on every
build, so a published run is one directory and no config edit.

## The worker

`site/wrangler.toml` follows `cnft.dev-workers/projects/notebooks/wrangler.toml`:

```toml
name = "agent-playbook-site"
compatibility_date = "2026-11-13"

[build]
command = "./build.sh"

[assets]
directory = "./dist"
not_found_handling = "404-page"

[env.dev]
routes = [{ pattern = "playbook-dev.defrag.au", custom_domain = true }]

[env.production]
routes = [{ pattern = "playbook.defrag.au", custom_domain = true }]
```

`not_found_handling = "404-page"` is what keeps `/runs/<id>/` a direct link. `build.sh` installs
from the lockfile, clears `.observablehq/cache/data` (the loaders read files the cache cannot see),
runs `observable build`, and copies `frontend/build` to `dist`.

## Publishing a run

Publishing is a runner flag, not a second tool:

```sh
cargo run --manifest-path integrations/rig-eval/Cargo.toml -- \
  --out .tmp/rig-eval-ladder --publish site/artifacts ...

# or re-publish an existing measured run
cargo run --manifest-path integrations/rig-eval/Cargo.toml -- \
  --reuse .tmp/rig-eval-ladder --out .tmp/re-export --publish site/artifacts

cd site && npm run build
wrangler deploy --env production
```

`--publish` writes one `<run-id>` directory. The id is `run-<started_ms>-<corpus7>-<model-slug>`,
so it sorts by time and names the inputs.

The publish step:

- requires a manifest — a run that never recorded its corpus, checkout and snapshot is not a
  publishable measurement;
- refuses a dirty checkout. A dirty run is a development run; the site says what it measured or it
  does not publish;
- refuses a run with a contaminated result. `traces.json` keeps every row, so the site would
  otherwise publish the run that saw the answer;
- writes the **public projection**: `answer` and `session` are dropped from every trace row,
  `workdir` and raw streams never ship, and `tools.json`/`checks.json` keep the rows the site
  charts;
- writes `observable.md` beside the data, so the notebook is part of the artefact. The notebook
  is authored markdown in `integrations/rig-eval/observable/notebook.md` and compiled into the
  runner, so a chart change is a reviewed edit rather than a string built in Rust;
- copies `claim.md` from the run directory when one exists. It never writes a claim; if the run
  has none, the site's run page says the tables are generated and uninterpreted.

The `manifest.json` gains `schema_version` (`1`). The site loaders check it and fail `npm run
build` on a mismatch, rather than charting a re-shaped export.

## The pages

- **`/`** — what the toolkit is, what the benchmark measures, the latest run's headline, and a
  link to the method before the numbers.
- **`/method/`** — the corpus fingerprint and schema, scoring and precision, isolation and
  contamination, the cost normalisation (input includes cache), the ladder, and what the numbers
  do not license. A public reading of `docs/design/benchmark-artifact.md`.
- **`/runs/`** — every published run: date, model (linked to the run, with a `tables` link),
  arms, runs, pass rate, cost.
- **`/runs/<id>/`** — the authored claim (or a visible absence), then the notebook. It leads with
  the claim the run is making, then six charts: cost per solved run; one dot per run against
  cost per passed check; a solved-by-scenario dot matrix sorted by the spread between arms; the
  share of runs that reached the toolkit (plugin, CLI, skill); tool calls split plugin versus
  everything else; and input tokens split cached versus fresh. A misses table closes it.
- **`/runs/<id>/tables`** — the generated `summary.md`: pass rate, score spread, cost matrices,
  diagnostics, adoption, solved-by-scenario, misses, tool evidence and the generated limits.

## Charts, not a table dump

The run page is a notebook, and the notebook is the artefact's `observable.md`. The generated
tables are a second page, because a reader arriving at a run wants the shape of the result before
the record of it.

The charts exist to answer, in order: what did a solved run cost; is the spread under that
aggregate; where does the ladder separate; did the arms reach the toolkit; what did the model
read. Every chart takes its colour domain from the arm order, so a colour means one arm on every
figure.

Two Observable Framework traps cost an afternoon and are worth knowing:

- **A trailing semicolon on a cell makes it a statement.** `Plot.plot({…});` in a cell returns
  `undefined` and renders nothing, with no error in the page or the console. Drop the semicolon
  from an expression cell; a cell that only declares `const`s is unaffected.
- **Plot does not dodge bars by fill.** Four arms on one categorical x draw on top of each other
  and the last one wins. Use a facet, a dodged dot plot, or a matrix.

Every `Plot.plot` passes Framework's reactive `width`, or the chart renders at Plot's default
640 px and the page scales the whole SVG down — text included — at a narrow width.

The site never recomputes a number from raw streams. Every figure is read from the run's exported
JSON or copied from `summary.md`; if a page disagrees with the run directory, one of them is a bug.

## What it is not

- **Not a service.** No worker runtime, bindings, D1, R2 or API. A run is immutable files, so the
  site is cacheable and has no secrets.
- **Not a leaderboard.** The method page names the model, the corpus and the platform; a different
  model is a different experiment.
- **Not the evidence archive.** Raw streams and effect logs stay in the private run directory. The
  public artefact is the projection above, reviewed before it is committed.
- **Not a per-run worker.** Adding a run is one directory under `artifacts/`, then a build and a
  deploy.

## Build and deploy

```sh
# from the repository root
direnv exec . bash site/build.sh          # artefacts → dist/
cd site && wrangler deploy --env dev      # public dev
cd site && wrangler deploy --env production
```

The site build is not part of `cargo test`. A CI job that runs `site/build.sh` is enough to catch
a broken artefact or a loader schema mismatch; deploys stay user-driven.
